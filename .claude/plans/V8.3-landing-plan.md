## 2. Architecture

### 2.1 Where `/` lives

- **A (rec) Pages Router, like /learn.** `pages/index.tsx` (static, no `getServerSideProps`), `src/app/page.tsx`
  deleted (Next refuses the same route in both routers). It reuses `Teacher`, the room and the director as they are.
  The metadata moves into `<Head>` the way `pages/demo.tsx` writes it; the theme script is already in
  `_document.tsx`; `/opengraph-image`, the icons and the App Router layout stay for every other route.
  - Cost: the landing's server components become client components, so their markup ships as JS.
  - Pages Router shared JS is 101 kB (framework 44.8, main 34.7, CSS 14.1, other 7.75) against 103 kB on the App
    Router, so the estimate is 101 + about 15 to 25 kB of landing = 116 to 126 kB, under 135.
  - **The first commit is a go/no-go spike:** move today's landing to `pages/index.tsx` unchanged and read the
    build. If it is over 125 kB before any new work, I stop and come back to you with B.
- **B App Router `/` plus vanilla three.** The stage in plain three.js (no react-reconciler, so the React 19 alias does
  not bite), the pure director from `src/lib/avatar` reused. Keeps server components, but re-implements Teacher's
  rig binding, masks, look, face and lipsync outside R3F: a second avatar runtime to keep in sync. Not worth it.
- **C App Router `/` plus a same-origin iframe** of a Pages Router `/stage`, driven synchronously through
  `iframe.contentWindow`. Two React apps in memory, two framework loads; rejected.

**One shared-code change** (needs your OK): `Teacher.tsx` gets an optional `signals` prop, a function returning
`DirectorSignals` plus reaction events, defaulting to today's store read. The landing drives the director from the
scroll timeline instead of writing into `useAristoStore` (the store is shared with /demo in the same app, and phase
and role come from `activeLesson`). `src/lib`, `src/store`, `src/hooks`, `src/app/api` stay untouched. Regression
proof: the director tests unchanged, /demo anchor probes identical, and a frame hash of the /demo teacher at fixed
times identical before and after.

### 2.2 Performance plan

- **First paint:** static HTML, the poster through `next/image priority` (LCP), fonts as today. The first-load JS is
  the page markup, the theme toggle and a 1 kB capability gate. No three, no animation code, no shaders.
- **After first paint** (`load`, then `requestIdleCallback`, and only if the gate says "full"): `import()` the stage
  chunk (three, R3F, drei parts, the director, the scroll driver, the shaders; about the /demo scene chunk, 350 to
  400 kB compressed), then room + Jake, then the clip pack after `sceneReady`, then the heart model when `#how` is
  within 1.5 viewports, then `teaching.jpg` / `source.jpg` with it.
- **No layout shift:** every pinned section has its height in CSS from the start; the poster and the canvas share
  one fixed box; text overlays are absolutely positioned inside pinned frames. CLS measured (target 0.00).
- **Frame budget:** DPR clamped to [1, 1.5], drei `PerformanceMonitor` drops to 1 on a sustained dip; the canvas stops
  rendering (`frameloop="never"`) when no 3D section is on screen (parents, footer).

### 2.3 Animation engine

| Option | Bytes (gz, lazy) | Support | Fit |
|---|---|---|---|
| **A (rec) Own scroll driver + CSS sticky** | about 2 to 3 kB | everything with sticky and rAF | One source of truth: section progress computed once per frame, read by 3D and DOM alike |
| B GSAP + ScrollTrigger | about 45 kB (free licence since 2025) | everything | Nicer timeline authoring; pin spacers fight sticky layouts and R3F's own loop, so it would be a second clock |
| C Motion (`framer-motion/dom` `scroll` + `animate`, already a dependency) | about 5 to 15 kB | everything; uses ScrollTimeline where native | Good for DOM; still needs a bridge into the R3F loop |
| D Native CSS scroll-driven animations | 0 | Chrome/Edge 115+, Safari 26+; Firefox behind a flag | Cannot drive WebGL; would need A anyway, so two systems |

**A in detail:** one passive scroll listener marks "dirty"; **R3F's own `useFrame` (one render loop)** reads
`scrollY` once, computes each pinned section's progress from cached offsets (re-measured on resize only), applies
spring damping, then writes the 3D state and the DOM overlays through refs (`transform`, `opacity`, one `--p`
custom property per active frame). No React state changes per scroll frame; React only re-renders when a beat
boundary changes which overlay is mounted. Easing, springs and keyframe helpers are small pure functions with unit
tests. The lite path runs the same driver on a plain rAF.

Scroll itself is native. No scroll hijacking or smooth-scroll library: the softness is in the damping of what
scroll drives, which keeps keyboard, screen readers and find-in-page intact.

## 4. Fallbacks (the lite version tells the same story)

The gate decides "full" or "lite" before any heavy download:

- **Lite if any of:** `prefers-reduced-motion`; no WebGL2 or `failIfMajorPerformanceCaveat` fails (software GPU);
  viewport under 768px or a coarse pointer without a fine one (phones); `navigator.connection.saveData`;
  `deviceMemory < 4`.
- **And after the fact:** the full stage measures its first 90 frames; if p75 > 24 ms, it hands over to lite (the
  canvas fades out and the stills take its place at the same scroll position).
- **Lite, motion allowed** (phones, weak GPUs): the same sections and copy. The pinned sections keep their sticky
  frames but show stills that cross-fade per beat (CSS opacity driven by the driver), the centrepiece as a four-frame
  strip (noise, sketch, diagram, model), the map as the same SVG with the same animation (it is DOM, cheap). A **See it
  in 3D** link goes to `/demo`.
- **Reduced motion:** no pinning at all: a plain vertical stack, every beat as a still with its caption, the map
  fully drawn at its end state, nothing animates (the `--dur-*` tokens are already 0 there).
- **No JS:** the stack as reduced motion (the `noscript` rule the page already has).

**Choice for you:** phones on lite by default **(rec)**, or full 3D on phones with a strong GPU (5.9 MB of assets on a
cellular connection, and the frame test decides after the download).
