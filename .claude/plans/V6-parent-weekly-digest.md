# V6 — Parent Weekly Digest

**Model:** sonnet | **Tier:** VISION | **Depends on:** T10 (Resend must be wired)
**Product thesis:** The student is the user; the PARENT is the customer. Today parents have
zero visibility, so there is nothing to justify paying when the approval gate becomes a
paywall. A weekly email — "what Hamza learned, where he's strong, what he's practicing" —
is the cheapest possible feature that creates willingness-to-pay, and every ingredient
(analytics route, mastery tables, Resend helper) already exists.

## Design

1. **Parent email capture**: add `parent_email` (nullable) to `profiles` (migration).
   Collect at onboarding as an optional 4th step ("Want a weekly progress email sent to a
   parent or guardian?") + editable in a small settings surface. Validate with Zod; send a
   one-time confirmation email with an unsubscribe link (`digest_opt_out` boolean +
   signed token — no auth required to unsubscribe; keep the token simple HMAC).
2. **Digest content** (one screen, skimmable, brand-styled HTML email):
   - Headline stats: active days, time on task, concepts advanced, reviews done.
   - "Strongest this week" + "Working on" (2-3 concepts each, plain-language names).
   - One warm narrative paragraph generated by `MODELS.fast` (Haiku) from the same analytics
     JSON — factual, encouraging, no grades-shaming, no fabrication (prompt must say: only
     reference provided data; if a field is empty, omit it).
   - CTA: "Ask them what a {coolest concept this week} is."
   - Nothing sensitive: no raw scores, no misconception details, no comparisons to other kids.
3. **Delivery**: Vercel Cron (`vercel.json` / crons config) hitting `POST /api/cron/parent-digest`
   Sunday evening; the route (protected by `CRON_SECRET` header check) iterates opted-in
   users with activity that week, builds analytics (reuse the logic behind
   `/api/profile/analytics` — extract shared helper rather than HTTP self-call), renders the
   email (react-email or plain template literal — keep deps minimal; Resend supports both),
   sends via the existing Resend helper, logs to a `digest_log` table (user, week, status)
   for idempotency — a rerun must not double-send.
4. **No-activity weeks**: skip the email entirely (an empty digest reads as nagging).
5. **Cost**: one Haiku call per active opted-in student per week — negligible; still log to
   `usage_events`.

## Acceptance criteria

- Opt-in flow works end-to-end; confirmation + unsubscribe verified (unsubscribe works
  logged-out).
- A real digest email renders correctly (Gmail + mobile), contains only true data, and the
  cron route is idempotent (rerun -> no duplicate sends) and rejects requests without the
  secret.
- Migration + RLS clean; `yarn type-check` + build pass.

## Do NOT

- Never email without explicit opt-in. No child PII beyond first name in the email.
- No LLM freedom to invent achievements — data-grounded prompt only.
